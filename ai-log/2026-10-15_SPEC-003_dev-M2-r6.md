### R-240 — 띠 해제 판정 높이: `100svh` 탐침 (공용 `watchBarRelease`)
- **고른 것**: 작은 뷰포트 높이를 `100svh` **탐침 요소**의 높이로 잰다(`src/ui/barRelease.ts#createSmallViewport`). 탐침은 `position: fixed; width: 0; height: 100svh; visibility: hidden; pointer-events: none; aria-hidden`라 문서 길이·스크롤·포커스·고정 요소 수집에 영향이 없다. `svh`를 모르는 브라우저(Chrome 108 미만·Safari 15.4 미만·Firefox 101 미만)는 `document.documentElement.clientHeight`로, 그것도 0이면 `innerHeight`로 물러난다(코드의 `innerHeight`는 이 한 곳뿐 — `tests/barRelease.test.ts`가 센다).
- **왜 `clientHeight`가 아니라 `svh`인가 (근거, 실기기는 못 봤다)**: `svh`는 CSS Values 4가 정의한 값 — 동적 도구 모음(주소창)이 모두 **펴진** 가장 작은 뷰포트 — 이라 정의상 스크롤로 변하지 않고 엔진마다 같은 뜻이다. `documentElement.clientHeight`는 레이아웃 뷰포트(초기 포함 블록) 높이인데, 모바일 엔진마다 주소창 접힘에 반응하는 방식이 다르다(Chrome Android는 주소창이 접히면 초기 포함 블록·`position: fixed`의 기준이 커지는 것으로 알려져 있고, iOS Safari는 도구 모음이 보일 때의 높이를 돌려주는 경향이 있다 — 엔진 동작 지식이며 이 환경에서 실기기로 확인하지 못했다). 한쪽 엔진에서 흔들릴 수 있는 값을 판정에 쓰는 것보다 명세가 보장하는 값을 쓴다. 데스크톱 크로미엄에서는 `100svh`가 `innerHeight`와 같아(둘 다 가로 스크롤바를 포함한다) **66조합 결과가 r5와 똑같다** — 해제 4조합 그대로.
- **히스테리시스는 넣지 않았다**: 작은 뷰포트 높이는 주소창에 흔들리지 않아 문턱을 둘로 나눌 이유가 없다. 명세 문구 「절반을 넘으면」 그대로다(`BAR_RELEASE_RATIO` 0.5).
- **공용 위치**: 측정·판정·`--bar-h`·`bar-released`·`ResizeObserver`·`resize` 리스너를 `watchBarRelease(bar, { onRelease, onReleasedResize })`로 `src/ui/barRelease.ts`에 모았다 — M3(룰렛·출생신고)·M4(대시보드)의 하단 띠가 같은 함수를 부른다. `TitleScreen`의 layout effect는 `has-bottom-bar` 클래스(첫 화면 전용)와 포커스 맞춤 콜백만 남겼다. 이 이동 때문에 `tests/barRelease.test.ts`·`tests/titleScreen.test.tsx`가 `TitleScreen.tsx` 소스에서 찾던 문자열 단언(`new ResizeObserver(apply)`·`setProperty('--bar-h'` 등)을 **같은 단언 그대로 `barRelease.ts` 소스로 옮겼다**(아래 「바꾼 기존 테스트」).
- **시험**: (1) 단위 — 가짜 `window`·`document`·`ResizeObserver`로 `innerHeight`·`clientHeight`·탐침 높이·띠 높이를 따로 바꿔 본다: innerHeight만 7번 바꾼 resize에서 `bar-released` 토글이 첫 측정 한 번뿐, 고정 쪽도 토글 추가 0. (2) e2e — 실제 브라우저에서 `Object.defineProperty(window, 'innerHeight', …)` + `resize` 이벤트를 6번 보내며 `MutationObserver`로 `<html class>` 변화를 센다: **해제(320×256 확인 단계 59%)·경계(667×375 글자 200% 확인 단계 56%)·고정(360×740 새 판 9%)·고정(320×568 이어하기 21%) 4조합 모두 변화 0번**. 공허 통과 방지로 「옛 방식(innerHeight로 판정)이었다면 뒤집혔을 흉내 값」이 조합마다 있었음을 센다. 별도 시험이 「진짜 창 크기 변화는 따라간다」(innerHeight를 900으로 흉내 낸 뒤에도 진짜 뷰포트 256에서 풀리고 568에서 고정으로 돌아옴)를 본다.

## r6 후속: 강제 색상 주 버튼 hover (마스터 지시)
- **원인**: `tokens.css`는 강제 색상에서 `--c-brand-hover`를 `ButtonText`로 매핑하고, `title.css`의 보통 모드 규칙 `.btn--primary:hover { background: var(--c-brand-hover) }`는 강제 색상 블록의 `.btn--primary { background: ButtonFace; color: ButtonText }`(특이도 (0,1,0))보다 구체적((0,2,0))이라 hover 때 이겼다 → 배경 = `ButtonText`, 글자 = `ButtonText`(라이트에서 둘 다 `rgb(0, 0, 0)`). 이 버튼은 `forced-color-adjust: none`이라 브라우저가 대신 고쳐 주지도 않는다. **다크 + 강제 색상에서는 더 다른 모양**이었다: 배경 `rgb(203, 214, 242)`(다크 팔레트의 `--c-brand-hover`)에 글자 흰색, 대비 1.45:1.
  - 다크에서 시스템 색이 아닌 값이 나온 이유(관찰): `tokens.css`의 다크 블록 `:root:not([data-theme='light'])`(특이도 (0,2,0))가 강제 색상 블록 `:root`((0,1,0))보다 구체적이라, 다크 OS + 강제 색상에서는 강제 색상의 시스템 색 매핑이 **다크 팔레트에 진다**. `tokens.css`는 designer 소유라 손대지 않았다(마스터 지시). 지금은 title.css가 `forced-color-adjust: none`인 요소(주 버튼·선택된 카드·점·로고)의 색을 시스템 색으로 직접 정해 영향이 없고(아래 전수 점검이 다크에서도 통과), 같은 패턴이 M3·M4 화면에 오면 같은 함정이 있다 → designer가 보면 좋은 항목(`tokens.css` 강제 색상 블록의 특이도).
- **고침**(`src/styles/title.css`, 강제 색상 블록의 `.btn--primary` 바로 아래): 상태마다 배경·글자를 **한 짝의 시스템 색**으로 못 박는다.
  - `.btn--primary:hover, .btn--primary:active { background: Highlight; color: HighlightText; }` — 눌릴 수 있다는 변화도 보이고(쉬는 상태 ButtonFace → hover Highlight) 시스템이 보장하는 짝이라 대비가 유지된다.
  - `.btn--primary:focus-visible { background: ButtonFace; color: ButtonText; }` — 키보드 포커스는 기본 짝 그대로(링은 outline이 그린다).
  - `.btn--primary:focus-visible:hover, …:active { background: Highlight; color: HighlightText; }` — 포커스 중 hover·active(특이도 (0,3,0))가 위의 포커스 규칙에 지지 않게.
- **전수 점검**(첫 화면 CSS의 `:hover`·`:active`·`:focus` 규칙을 모두 찾았다 — `:hover`는 이 한 곳뿐이고 `:active`는 없고 포커스는 outline·`:focus-within` 링뿐): 같은 패턴의 다른 버튼 — 보조(`.btn--secondary`)·고스트(`.btn--ghost`)·캐러셀 조작 버튼·라디오 카드 — 는 hover 규칙이 없어 바탕·글자가 `Canvas`/`CanvasText` 짝 그대로다. 규칙만 읽고 끝내지 않고 **e2e로 실제 계산 색을 쟀다**(아래).

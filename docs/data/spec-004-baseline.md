## 1. 이벤트 × 세대 × 나이 후보 칸

### 1-1. 센 방법

- 대상: `src/data/events/*.json` 이벤트 140개(결정 90 + 서술 50). 후보 = 단계(`stages`)와 나이 범위(`ageRange`)가 맞고 시대 제한(`eras`)이 통과하는 이벤트. **플래그·재력·스탯 조건은 보지 않는다**(SPEC-005 기준선과 같은 방식 — 상한). 그래서 「앞선 사건 없이 열리는 것(`conditions.flags` 없음)」을 따로 센다.
- 칸 = **세대 7 × 나이대 8**(TL3: 영유아 0~6 · 어린이 7~12 · 청소년 13~19 · 20대 · 30대 · 중년 40~54 · 장년 55~64 · 노년 65~100). 한 칸의 값은 세대의 모든 출생 연도 × 나이대의 모든 나이를 **쌍**으로 세어 평균을 낸 값이다. 「4 미만」은 SPEC MG2의 「(세대, 나이) 칸 후보 ≥ 4」 기준이다.
- 세대 7종(측정용 복사): 산업화·전후 1940~1954 · 베이비붐 1955~1963 · 86 1960~1969 · X 1970~1980 · 밀레니얼 1981~1996 · Z 1997~2012 · 알파 2013~2020.
- **시대 제한을 세대로 옮기는 규칙** (임시 — 어떤 규칙이 맞는지는 GM1이 정한다):
  - **U 상한**: 시대 제한을 무시한다. 모든 세대가 같은 값 — 세대 차이는 시대 제한에서만 생기므로 U는 「나이 구조만의 바닥」이다.
  - **L 하한(글자 그대로)**: 지금 모델의 `ERA_CONFIG[era].birthYears`(지난 1950~1989 · 지금 2026 · 다가올 2030~2060)에 출생 연도가 들어갈 때만 통과. 세대 범위(1940~2020)에는 지금·다가올 출생이 없다.
  - **R 중간(달력 연도 규칙)**: 이벤트 `eras`를 SPEC MG2가 만들 `yearRange`의 첫 근사로 옮긴다 — 지난 = 달력 연도(출생 연도 + 나이) ≤ cut, 지금 = ≥ cut+1, 다가올 = 달력 연도 ≥ 2026(전망 구간). 세 갈래 중 하나만 맞으면 통과. cut 1995 / **2000(주)** / 2005를 견줬다. 이 문서의 표는 별말이 없으면 R(2000)이다.

### 4-3. SPEC-004가 쓸 수 있는 여유

- **한도 400,000B 그대로 보면 여유는 26.6KB**(WebKit PC)다. SPEC 완료 기준 18은 「초기 로드 ≤ SPEC-003 기준(400KB▲) + 연표·계수·지역 데이터 증가분 ≤ 60KB▲ + BGM 증가분 ≤ 40KB▲」로 적혀 있어 **한도를 500KB로 읽을 수도 있다**(그러면 여유 126.6KB). 어느 쪽인지는 마스터가 정한다. 이 문서는 한도 400,000B(e2e-prod 시험이 지금 거는 값)를 기준으로 계산한다.
- **SPEC-004 증가분 어림**(현재 데이터 밀도에서 뽑은 대략 값, ±35%. GM1 설계 뒤 GM4·GM6·GM10에서 다시 잰다):

| 항목 | 어림 gzip | 근거(밀도) |
|---|---:|---|
| 연표 DB `timeline.json` (사건 ≥ 68, 변형 ≥ 244 = 체험·갈등 184 + 지역 체감 60) | 15~18KB | 변형 1개 ≈ 185B(원본) · 사건 메타 ≈ 250B · 한국어 JSON 압축률 약 25% (이벤트 JSON 122KB → 30.7KB) |
| 신규 이벤트(GE4 사연 세대마다 10개 안팎 + 알파 전용 ≥ 30 + 알파용 변형 ≥ 15) + 전망 사건 20~30(변형 3~5개) | 25~32KB | 이벤트 1개당 gzip 약 219B(30.7KB / 140) |
| `economyByYear.json` (해 × 열 ≥ 14, `cpi`는 DC4가 1965~2025 확보) | 6~9KB | 숫자 위주, 해 ≈ 130 × 열 ≈ 22 |
| 전망 지표 추가(지금 4개 → ≥ 12, 일부는 예비에 3개) | 10~25KB | 지표 1개당 평균 gzip 약 3.2KB |
| 이름 풀 확장(2008~2020 법원 연도 풀, 1940·1990·2000~2007 풀) | 3~19KB | 최상위 20명 목록만 쓰면 3KB, 시도별 합집합 650칸을 넣으면 최대 19KB |
| 세대 정의·카드 문구·시도 연혁 | 3~5KB | |
| 새 화면·로직 코드(세대 카드·시도 선택·연도 릴·연표 엔진·전망·생애 보드·당시 화폐 전환·BGM 전환) + CSS | 30~45KB | 지금 앱 코드 전체 약 135KB(JS)·CSS 14.5KB |
| BGM 장르 7종 악보 + 엔진 확장 | 12~25KB | 지금 엔진+악보 2KB(패턴 5개) → 장르 7 × 패턴 ≥ 4 |
| **합계(전부 첫 화면에 실으면)** | **약 105~180KB** | 한도 400,000B 기준 **여유(26.6KB)를 약 80~150KB 넘는다** |

### 4-4. 지연 로드가 필요한 덩어리 후보

「첫 화면(세대 선택)에 필요한가」로 가른다. 지금 구조에서 `EVENT_POOL`을 `core/life.ts`·`storage.ts`·`session.ts`·`gentle.ts`·`parentDecision.ts`가 **정적으로 import**하므로, 이벤트·인용·연표를 지연 로드하려면 이벤트 풀을 비동기로 받는 구조 변경이 필요하다(GM1 설계 항목).

| 덩어리 | 지금 gzip | 첫 화면에 필요? | 불러오는 때 | 비고 |
|---|---:|---|---|---|
| 이벤트 5개 JSON + 신규 이벤트·알파·전망 사건 | 30.7KB (+25~32KB) | 아니오 | 「태어나기」 이후(또는 저장 복원 때) | 정적 import 구조 변경 필요. 세대별 파일로 쪼개면 더 줄어듦 |
| `citations.json` (+ `citationInsights`) | 30.5KB | 아니오 | 결정 카드가 처음 뜰 때 | `citationsAccess.ts` 한 곳을 거치므로 분리가 쉽다 |
| `koreaStats.json` 중 첫 화면 표제어 19개(`STAT_HEADLINES`)를 **뺀 36개 지표** | 약 30KB (표제어 19개는 약 19KB) | 아니오 (19개만 첫 화면) | 룰렛·출생신고·엔딩 때 | 예비 묶음 패턴(`loadReserveStats()` + `import()`) 재사용. 추가될 전망 지표는 처음부터 이쪽 |
| 이름 풀(+ 연도별 풀 확장) | 7.3KB (+3~19KB) | 아니오 (출처 문구 `meta`만 첫 화면 FAQ에 쓰임) | 룰렛 화면 | 출생 연도가 정해진 뒤 필요. `meta`와 풀을 갈라야 한다 |
| 연표 DB·`economyByYear`·세대별 전망 | (+25~40KB) | 아니오 | 인생 시작 때 | 세대별로 쪼개면 해당 세대 연도만 받는다 |
| BGM 장르 악보·엔진 확장 | 2KB (+12~25KB) | 아니오 | 사용자가 BGM을 켤 때만(기본 꺼짐) | `import()` 한 곳. `bgm-lab`은 배포 제외 |
| 화면 코드(`LifeScreen`·`EndingScreen`·`NoteSheet`·차트·기록) | ≈ 41KB(ui+screens) | 아니오 | 화면 전환 때 | `React.lazy` 라우트 분할 |
| 얼굴 레이어 | 3.9KB | 아니오 | 출생 이후 | |
| 첫 화면 큰 그림(PC) | 65.1KB | 예 | — | 한도의 16%. 더 줄이면 여유가 직접 늘어난다 |

- 위에서 **이벤트·인용·이름 풀·첫 화면 밖 지표(따로 gzip 약 99KB, 환산 약 91KB)를 지연 로드하면 첫 화면 합계가 약 275~285KB로 내려가 한도까지 약 115~125KB의 여유**가 생긴다. SPEC-004의 새 데이터(어림 100KB 안팎)가 처음부터 지연 덩어리면 첫 화면은 지금과 비슷하게 유지된다. 반대로 지연 로드 없이 새 데이터를 지금 묶음에 더하면 한도를 넘는다.
- **주의**: `initial-load.spec.ts`는 `networkidle` 뒤 1.5초 안에 받은 모든 응답을 센다. 첫 화면 직후 유휴 시간에 미리 받기(prefetch)를 하면 그만큼 합계에 들어가므로, 「미리 받기를 초기 로드로 셀지」를 마스터가 정해야 한다.

## 6. 연표 줄 시간 여유 추정

TL13의 「줄당 4초▲」 가정에서 한 판에 넣을 수 있는 연표 줄 수(= 여유 ÷ 줄당 시간, 내림). 여유는 5절의 시대별(36.5분 − 지금 값)과 평균(35분 − 평균)이다. 지금 모델의 상수로도 같이 계산했다.

| 시대 | 여유 | **줄당 4초(SPEC TL13▲)** | 줄당 8.44초 (이미 사건이 있는 해에 한 줄 더 — `extraLineMs` × 1.6875) | 줄당 16.88초 (조용한 해가 서술 해로 바뀜 — (서술 17초 − 조용 7초) × 1.6875) | 섞은 값 (조용한 해 53~55% 가중, 줄당 약 13초) |
|---|---:|---:|---:|---:|---:|
| 지난 | 5.66분 | **84줄** | 40줄 | 20줄 | 26줄 |
| 지금 | 1.99분 | **29줄** | 14줄 | 7줄 | 9줄 |
| 다가올 | 1.62분 | **24줄** | 11줄 | 5줄 | 7줄 |
| 세 시대 평균 기준 | 1.59분 | **23줄** | 11줄 | 5줄 | — |

- **줄당 4초 가정으로는 가장 빠듯한 시대도 24줄**이고, 완료 기준 10의 목표(판당 연표 줄 평균 ≥ 12, 알파 ≥ 6)는 12줄 × 4초 = 48초 = 0.8분으로 여유(1.6~2.0분)에 들어간다.
- **그러나 지금 모델의 상수로 같은 12줄을 넣으면** 줄당 13초 가정에서 2.6분이라 지금·다가올의 여유 1.6~2.0분을 넘는다. 실제 연출 타이머(`holdMsFor`)는 해마다 대기를 계수로 정하므로, 연표 줄이 앉은 조용한 해는 서술 해(28.7초)가 되고 이미 사건이 있는 해는 줄당 8.44초가 더해진다. **TL13의 4초 모델과 실제 타이머가 어긋나지 않게, 연표 줄이 연출 대기에 미치는 영향(전용 짧은 대기 상수를 둘지, 서술 해를 그대로 쓸지)을 GM1에서 정해야 한다.**
- 카드 1장 ≈ 0.52분(31초, content-M8)이므로 카드 1장을 덜어 내면 줄 7.8개(4초) / 3.7개(8.44초) / 1.8개(16.88초) 자리가 난다. 단 카드 수 판정 하한까지 덜어 낼 수 있는 장수는 지난 0.6장(총)·0.6장(본인), 지금 1.4 / 1.5장, 다가올 1.7 / 1.8장뿐이라 TL13의 「일반 카드 수를 조정한다」는 완충은 1~2장이 한계다.
- 연표 줄 상한이 시대별로 3배 이상 다르다(84줄 대 24줄). 세대 7종 기준선에서 시대별 값이 갈라지면 줄 수 목표를 세대별로 둘지 정해야 한다.

## 7. 측정의 한계와 마스터가 정할 것

**한계**
1. 후보 칸은 플래그·재력 조건을 보지 않는 상한이다(플래그 없는 후보를 따로 병기). 한 이벤트는 대부분 `once`라 후보 4개가 그 나이 4번의 사건을 뜻하지 않는다.
2. 시대 제한을 세대로 옮기는 규칙 R의 컷(1995 / **2000** / 2005)은 임시다. 결과는 56칸 중 채움 42~44칸으로 컷에 민감하지 않다.
3. 연표 후보의 연도는 부록 A의 초안 값이다(DC1이 확인 전). 소재 창고 항목의 시기·나이대는 문장을 읽어 옮긴 근사다.
4. 경로 지표는 `lifeBoard`·일 슬롯이 없는 지금 모델을 플래그·주거로 대리한 정의 v0이다. 지금 모델은 시대 안에서 출생 연도가 판에 영향이 없어 X와 밀레니얼을 가를 수 없다(지난 = X 대리, 지금 = 밀레니얼 대리).
5. 판 길이와 번들은 v0.2.1(`687c003`)과 같은 `src`의 값이다. SPEC-004 구현이 들어가면 모두 달라진다.

**마스터가 정할 것 (제안 포함)**
1. **AL10 ①(경로 엔트로피 1.5배) 정의 교체**: 지금 정의는 표본 상한 때문에 1.06배가 최대다. 나이별 5축 벡터 엔트로피 평균(지금 4.3~4.6비트)이나 정규화한 값으로 바꿀 것을 제안.
2. **AL10 ②·③ 기준 숫자**: N잡 X 기준선 17.3%(엄격), 정석 4단 X·밀레니얼 3~4%(AL10식)는 SPEC의 「X ≤ 15%」·「≥ 35%」와 맞지 않는다. 판정 정의(일 슬롯 기반)를 X·밀레니얼에도 적용해 GM9에서 다시 재는 것으로 하고, 그 전까지 숫자를 ▲로 둘 것을 제안.
3. **번들 한도 해석**: 400,000B 고정(여유 26.6KB) 대 완료 기준 18의 합산(500KB). 어느 쪽이든 지연 로드를 GM1 설계에 넣을 것을 제안(4-4절).
4. **TL13의 4초 가정**: 모델 상수와 어긋남(6절). 연표 줄이 연출 타이머에 주는 영향의 정의를 GM1 설계에 넣을 것을 제안.
5. **시대 제한 33개의 `yearRange` 전환**(MG2): 22개는 글자 그대로는 후보가 없다. 컷 연도와 `infant-care-alert`·`infant-talking-toy` 처리(다시 쓰기 대 폐기)는 GM1에서.
6. **소재 창고 요청 후보 칸**(1-6절): ① 노년기 생활 디테일·나이별 걱정거리(세대 구분 없이) ② 1940~50년대 어린 시절(영유아~청소년, 1940~44년 공백) ③ 영유아기(0~6) 부모 시점 소재 ④ Z·알파 초등 시기(2004~2032)의 실제 연도 생활 ⑤ 20세 전후(졸업·성인 첫해).

## 마스터 결정 (2026-10-27 — GM0 「마스터 확인이 필요한 것」)

1. **번들 한도**: 완료 기준 18은 **초기 로드 400,000B 고정**으로 읽는다(첫 화면이 빠른 것이 PC·Android 모두의 첫인상). SPEC-004가 더하는 것(연표 DB·세대 설정·`economyByYear`·전망·BGM 악보)과 지금의 이벤트·인용·이름 풀·첫 화면 밖 지표는 **지연 로드**로 옮긴다 — 불러오는 시점은 「태어나기」(판 시작) 이후이고, 첫 화면 유휴 중 미리 받기(prefetch)는 하지 않는다(`initial-load.spec.ts`의 셈을 바꾸지 않는다). `EVENT_POOL` 정적 import 구조 변경은 GM4에서.
2. **연표 줄 시간(TL13)**: 「줄당 4초」 가정은 실제 연출 타이머와 어긋나므로 버린다. GM1이 `holdMsFor`에 연표 줄을 넣는 규칙을 정한다 — 기준: 조용한 해에 연표 줄이 앉으면 서술 해 전체 대기(28.7초)가 아니라 **연표 줄 전용의 짧은 대기**를 둘지 designer와 함께 정하고, 판당 연표 줄 목표(약 12줄)가 M24 구간(평균 ≤ 35분, 시대별 ≤ 36.5분) 안에 들어오게 한다. 들어오지 않으면 줄 수를 줄이지 말고 마스터에게 보고(형진 님 원칙 「몰입·밀도」 — 구간 재조정은 마스터·형진 님 결정).
3. **AL10 지표 정의 교체**: ① 「알파 ≥ 밀레니얼 1.5배」는 경로 엔트로피가 상한에 붙어 있어 **나이별 5축 벡터 엔트로피**로 바꾼다 ② ③의 절대 숫자(X ≤ 15% N잡, X·밀레니얼 정석 4단 ≥ 35%)는 지금 모델과 맞지 않으므로 GM1에서 **공식 통계 근거**(세대별 혼인·출산·자가 보유·다중 일자리 비율)를 찾아 다시 정한다.
4. **현실성 점검(형진 님 원칙)**: 정석 4단(취업·결혼·출산·내 집)을 모두 밟은 판이 3~4%뿐인 것은 실제 한국의 X·밀레니얼 세대와 크게 다를 가능성이 크다(플래그가 특정 사건에만 켜지는 구조 때문일 수 있음). GM1은 이 숫자를 공식 통계(코호트별 혼인율·출산율·자가 보유율)와 견주는 **현실성 보정 항목**을 설계 문서에 넣는다 — 숫자를 맞추려 지어내지 않고, 통계가 확인되는 범위에서.
5. **시대 제한 33개의 `yearRange` 전환**: 주 규칙(달력 연도 2000 기준)을 출발점으로 GM1에서 이벤트별로 확정하고 reviewer가 판독한다. 고아 2개(`infant-care-alert`·`infant-talking-toy`)는 해당 기술이 있는 연도로 `yearRange`를 준다.
6. **소재 창고 요청**: 노년기 생활(65세 이후), 1940~50년대 어린 시절, 영유아기 부모 시점, Z·알파 초등 시기, 20세 전후 — 소재 창고 `03_마스터요청/요청.md`에 올린다.

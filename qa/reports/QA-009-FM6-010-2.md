## 3. FAIL 목록

### F1 [버그 — 시험 도구(작업자), 앱은 정상] 제품 번들 CSS 시험이 새 `@supports selector(:has(*))`를 못 풀어 던진다
- **재현:** `npm run e2e:prod`(또는 이미 빌드한 뒤 `./node_modules/.bin/playwright test -c playwright.prod.config.ts e2e-prod/smoke.spec.ts:697 --project=chromium`). 매번 같다(결정적 — 두 번째 실행도 실패). 1회차 `e2e:prod`는 이 시험이 통과(33 통과 · 1 건너뜀)였다.
- **오류:** `Error: browserCss: 지원하지 않는 @supports 조건: selector(:has(*))` — `tests/helpers/browserCss.ts:52`(`evaluateSupports`) ← `cssAppliedBy` ← `e2e-prod/smoke.spec.ts:746`(⑤ 모르는 브라우저가 걸러 낸 번들 CSS).
- **원인(읽은 코드):** 커밋 `5c218d6`가 `src/styles/dash.css`에 `@supports selector(:has(*)) { .log__list { scroll-padding-top: calc(var(--log-jump-bottom, 0px) + var(--sp-3)); } .log__list:has(.log__jump:focus) { scroll-padding-top: var(--sp-3); } }`를 넣었다. 번들 CSS에 그대로 남는다(`dist/assets/*.css`에 `@supports selector(:has(*)){`). 그런데 `evaluateSupports`는 `[not] (속성: 값)` 꼴 하나만 풀고 다른 꼴은 「조용히 틀리지 않도록 던진다」(주석 그대로)라서 `selector(...)`에서 던진다. 이 시험도우미를 쓰는 다른 시험(`tests/docCssFallback.test.ts` 13개 · `e2e/m3-css-fallback.spec.ts` 6개)은 번들 전체가 아니라 특정 CSS만 읽어 통과한다(내가 돌려 확인).
- **앱은 정상:** 이 `@supports`는 Chromium·WebKit에서 동작한다(R2-03~06). 시험 쪽만 새 꼴을 모른다.
- **권고(작업자, 코드는 내가 고치지 않았다):** `evaluateSupports`에 `selector(...)` 꼴을 추가한다. 이 시험(⑤)은 「컨테이너 질의를 모르는 브라우저」의 걸러진 CSS를 보는데, 그 브라우저(Safari 15.4~15.6)는 `:has()`를 알므로 두 기능 집합(`NO_CONTAINER_QUERIES`·`WITH_CONTAINER_QUERIES`) 모두에서 참으로 두는 것이 맞아 보인다(판단은 작업자·검수). 고친 뒤 `npm run e2e:prod`(2분)만 다시 돌리면 된다. 검수자가 시험을 못 돌리고(읽기 전용) 작업자도 이 e2e를 안 돌린 것이 놓친 이유로 보인다 — 앞으로 `src/styles/*.css`에 새 `@supports` 꼴을 넣으면 `e2e:prod`가 닿는다는 점을 지시서에 적어 두면 좋다.
- 분류: **버그**(명세 누락 아님) — `tests/helpers/browserCss.ts`의 주석이 스스로 「다른 꼴은 던진다」고 정했고, 새 꼴을 CSS에 넣을 때 도우미를 넓히는 것이 작업자의 몫. 근거: REV-010-QAFIX-1「CSS 우선순위와 대체」(`@supports selector(:has(*))` 밖은 옛 동작) + 도우미 주석.

## 5. RECORD

1. **WebKit은 링크를 Tab 정지점으로 치지 않는다.** 같은 판에서 Chromium Tab 61칸·WebKit 59칸(`<a href>`인 「의견 보내기」 `tool-feedback`와 「시대의 창」 `A.era`가 빠진다). 그래서 `m4-focus` 알약 시험을 WebKit으로 돌리면 8조합 모두 「Tab 순회가 닿지 못한 조작 요소: tool-feedback, A.era」 한 줄로 실패하고 가림 위반은 0이다. 앱 문제가 아니고, 이 시험은 저장소 WebKit 프로젝트에 원래 없다. 앞으로 WebKit에서 포커스 감사를 돌리려면 `<a>`를 정지점에서 빼는 처리가 필요하다.
2. **WebKit의 마우스 클릭은 단추에 포커스를 주지 않는다**(Safari 계열 기본). 그래서 「알약에 클릭으로 포커스가 갈 때 12px」은 WebKit에서는 해당 경로가 아니다(포커스는 기록 영역으로, 여백은 알약 아랫변 + 12px가 맞다). Android Chrome(Chromium)은 누르는 순간 포커스가 가고 12px 복귀를 확인했다.
3. 짧은 화면(320×256·글자 200%)에서 알약(87px)이 영역의 큰 몫을 차지한다(알약 위치 top 80 · bottom 167 / 뷰포트 256px). 포커스를 옮기는 동안 방향 전환 스크롤은 없다. 알약에서 Tab으로 첫 「근거 보기」 단추로 가면 기록이 맨 위로 끌려 알약이 사라진다 — 설계대로.
4. 알약이 떠 있고 이동 대상 줄이 보이는 구간(영역 높이 − 위 여백 − 아래 여백)보다 클 때(320×568·글자 200%의 시대 줄 349px > 248px) `scrollIntoView({block:'nearest'})`는 줄의 아랫변에 맞춰 윗부분이 알약 밑에 남는다. 「시대의 창」 실제 클릭 경로에서는 줄이 맨 위라 안 나온다(R2-09). 키보드 포커스 이동(작은 단추)은 해당 없음.
5. `m7c-note:377`은 28.7~28.8초로 한도 90초에 마진이 충분하다(1회차 한도 30초에서 흔들렸던 시험).
6. 1회차의 두 지적(Tab 정지점이 해마다 늘어남, F2 0.5px 허용 구간 가운뎃점)은 이번 범위 밖이라 다시 보지 않았다.
7. 흔들림 두 건이 모두 「작업자 6 병렬 + 무거운 포커스 감사 시험」과 같은 실행에서 난 것이 공통점이다. 조용한 재실행에서 0건이라 시험 부하 의존이다(앱 문제 아님). 지금 작업자 수로 전체 e2e를 돌리면 가끔 날 수 있다.
